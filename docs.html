Documentation

Notes on how to make a CROW Card, what we mean by terms and categories, definitions for potential values, and so on. The information here may also be useful for community organizers choosing where and how to build an online space.

Getting Started

The MAKE feature assumes you've already set up (or at least selected) a system for your community to sit within. If you haven't, you may consider perusing the platforms section, which provides an overview of some common systems communities have used, alongside information we think is useful (because it can shape how much autonomy or power your community has!): whether the software is open source, whether you can host an instance of it yourself, what structural model it follows, and what costs you should expect.

By community, we take a pretty broad view: a group that engages in and enforces some kind of collective decision-making, has a shared (digital) space, has boundaries for membership, and some kind of shared purpose. However, this also excludes some informal or cultural communities we often colloquially refer to, e.g., a distinct subset of users on Bluesky. This is not to say those groups can't use the CROW Card Maker! We presume that there just wouldn't be a clear place to post the Card itself, nor clear mechanisms to enforce the values and practices that are stated on it.

Examples.

A Reddit subreddit qualifies: moderators set rules, and the community experiences them. A Facebook Group qualifies too, but note that Facebook can override or dissolve it unilaterally, which limits sovereignty. Likewise, Bonfire instances and other groups on community-oriented platform software generally count as communities (and in the case of Bonfire, some features may even result in some nested communities).

A TikTok account or just a social media feed does not qualify: there is no community governance surface, only an audience and an algorithm.

Some emergent systems also create some interesting new cases of online community: labeling services like Blacksky (built on AT Protocol) govern a normative filter, deciding whose content is visible to people who opt in, which is a real form of collective decision-making (but not for a shared venue in the traditional sense).

Getting started is simple. You can simply create a new Card by going to MAKE, entering some basic information about your community:

  • link
  • name
  • size
  • platform - this will infer what community type yours and accordingly, what modules you'll want to fill out in the CROW Card app. You can edit the type and module selection.
  • keywords - we recommend giving at least three
  • values - we recommend selecting at least five

Important!

When you create a new Card, the app will give you an id and secret key. Save it somewhere! You will only get this once and you can use it to edit/update your Card.

You may want to think about how your CROW Card will be filled out or updated. For example, some communities may want to convene town halls to have a participatory discussion about their governance practices, using the CROW Card app as an occasion to reflect, iterate, and document. Others might be simply run by one person who fills it out unilaterally. It will depend on your community (however, we do encourage using it as an excuse to convene)!

We do run workshops to help communities fill out the CROW Card. Reach out!

Coming Soon

We are actively working on improving the experience of using the CROW Card Maker. This includes:

  • Automating the filling in of fields so that folks don't need to type so much! For example, if you enter your link, ideally our app should check out the link and try to fill in as many later fields as possible (e.g., community name, size).
  • Providing recommendations for governance practices (e.g., conflict management, decision-making) based on earlier information shared (e.g., community values or even just description of what the community is about).
  • Integrating CROW Cards into existing platform software as extensions.
  • Forking from publicly shared CROW Cards in the Library.

Platforms

If you're really just getting started and have yet to select a digital home for your community, we have tried to collate and annotate some of the most common platforms that communities seem to sit within these days. Let us know if you believe a platform should be included here.

We label the following for each platform:

  • Software. What is the exact software being used?
  • Protocol. Is the platform based on an open protocol?
  • Open source. Is it considered OSS per OSI standards?
  • Self-hostable. Can one host their own instance of the software for their community (e.g., on their own server)?
  • Model. What kind of structural model describes how the infrastructure of the platform is organized?

These all impact how much technical and organizational work you may be on the hook for, how much autonomy and power you're likely to have, and some costs you might incur. You can look through Reference below to find definitions of these columns as well as community types, platform types, etc.

Platform types

We also think about the platform type, based on the labels (is it protocolized, is the software open source, is it self-hostable, what model does it follow). We use this to provides some reasonable estimates of potential costs of using that platform. It also makes it easier to compare platforms that look different on the surface but share the same underlying structure.

TypeDescription
Corporate / ProprietaryOperated by a company. Community runner is a tenant — no infrastructure to manage, but also no ultimate control.
Self-Hosted, Text-PrimaryYou run the software yourself. Primary content is text, links, or lightweight media. Full control; real infrastructure costs.
Self-Hosted, Media-HeavySelf-hosted with significant video or image storage. Storage and delivery costs are a meaningful ongoing expense.
Hosted OSS / InstitutionalOpen source software, but hosted by an institution (a university, a nonprofit). You participate; you don't operate.
Protocol Client, Relay-BasedConnects to the Nostr relay network. Infrastructure costs only arise if you run your own relay.
Protocol Client, PDS-BasedConnects to the AT Protocol network. Infrastructure costs only if you run your own Personal Data Server.
Centralized MessagingOpen source software, centrally operated by the developer. Community = a group chat. No infrastructure costs.

Expected costs

Rather than guessing costs platform by platform, costs are derived from each platform's type. The logic is simple: the main cost drivers are infrastructure ownership (do you host it?) and content type (does it generate heavy media?). Everything else — admin labor, third-party tools — applies broadly regardless of platform choice and depends more on your community's size and activity.

  • Self-hosting means you bear hosting, domain, email delivery, backups, and potentially managed hosting costs. Proprietary or institutionally-hosted platforms mean you bear none of these.
  • Media-heavy platforms (PeerTube, Pixelfed) add significant storage and delivery costs on top of the standard self-hosting baseline.
  • Protocol-native clients (Nostr, AT Protocol) have costs that only arise if you choose to run your own relay or Personal Data Server — most community runners won't.
  • Admin and moderation labor is the one cost that cuts across all platform types, because it follows community size and culture rather than technical architecture.

Some platforms have overrides where the type default isn't accurate — for example, Discourse requires SMTP for notifications (email delivery = Yes, not Sometimes), and Mailman is itself an email delivery system.

Structural models

The structural model describes how a platform's infrastructure is organized — who controls data, and how communication flows between participants.

ModelDescriptionExamples
CentralizedA single operator controls all data and infrastructure. The platform is one server (or cluster) owned and operated by one entity.Facebook, Reddit, Discord, Discourse (each instance)
FederationMultiple independently-operated servers interoperate via a shared open protocol. Each server is autonomous; users on different servers can still interact.Mastodon (ActivityPub), Matrix (homeservers), Mailman (email/SMTP)
RelayMessages are broadcast through relay nodes. Clients choose which relays to connect to and read from. There is no canonical server — the network is the relays.Damus, Amethyst, Primal (all Nostr)
Federation / RelayUses elements of both models. AT Protocol uses PDS-to-PDS federation for data storage, plus a relay layer (the firehose) for real-time distribution.Bluesky, Rsky (Blacksky)
Centralized / FederationA proprietary or institutionally-controlled platform built on top of a federation protocol. The platform itself is not self-hostable, but it interoperates with the broader protocol ecosystem.Roundabout (proprietary, built on AT Protocol)

Open source (OSI)

The Open Source Initiative (OSI) defines open source software as software whose license grants freedoms to use, study, modify, and distribute. The Open Source (OSI) column reflects whether the platform's software is released under an OSI-approved license.

A few cases worth noting:

  • Telegram — client apps are open source (GPLv3), but the server is proprietary and not published. Since the server is the operative component for a platform, Telegram is classified as not open source.
  • Signal — both client and server are AGPLv3, so it is open source. However, Signal controls the central infrastructure and the server is not practically self-hostable to interoperate with the main network, hence Self-Hostable = No.
  • Fandom — built on a proprietary fork of MediaWiki. Although MediaWiki itself is open source (GPLv2+), Fandom's modifications are not published under an OSI-compatible license.
  • Wikipedia — the MediaWiki software is open source (GPLv2+), but Wikipedia itself is hosted exclusively by the Wikimedia Foundation. The software label is open source; the platform is not self-hostable as Wikipedia.

Cost columns use a five-point scale. All values reflect what a community organizer or operator typically pays — not the platform company.

YesThis cost reliably applies to community operators on this platform.
NoThis cost does not apply.
OftenApplies frequently, but not universally — varies by community size or activity level.
SometimesApplies in some configurations or at some scale, but not by default.
