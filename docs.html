Platform dataset

A structured reference for community organizers choosing where and how to build an online space.

Overview

CROW Cards helps communities describe and share how they govern themselves. But before you can govern, you have to choose a platform — and that choice shapes what governance is even possible. This dataset catalogs the platforms a community might use, with consistent labels for the properties that matter most: whether the software is open source, whether you can run your own instance, what structural model it follows, and what costs you should expect.

The dataset is designed to pre-fill the platform section of a CROW Card. Every value can be edited; these are starting points, not verdicts.

How to read this. Platforms are grouped by community type (chat group, discussion forum, etc.). Within each group, generic protocol client rows let you specify any software that speaks that protocol — useful if your platform isn't listed by name.

What is a community?

For the purposes of this dataset, a community is a unit of collective decision-making — a group that can govern itself. That means it has some mechanism for making shared rules and enforcing them, even informally.

This definition does real work on the platform list. A Reddit subreddit qualifies: moderators set rules, and the community experiences them. A Facebook Group qualifies too, though with an important caveat — Facebook can override or dissolve it unilaterally, which limits sovereignty. A TikTok account does not qualify: there is no community governance surface, only an audience and an algorithm.

A few platforms sit in genuinely novel territory. Labeling services like Blacksky (built on AT Protocol) govern a normative filter rather than a place — they decide whose content is visible to people who opt in, which is a real form of collective decision-making, just not a venue in the traditional sense.

Platform types

Each platform is assigned one of seven types. The type determines the default cost profile and makes it easier to compare platforms that look different on the surface but share the same underlying structure.

Corporate / Proprietary

Operated by a company. Community runner is a tenant — no infrastructure to manage, but also no ultimate control.

Self-Hosted, Text-Primary

You run the software yourself. Primary content is text, links, or lightweight media. Full control; real infrastructure costs.

Self-Hosted, Media-Heavy

Self-hosted with significant video or image storage. Storage and delivery costs are a meaningful ongoing expense.

Hosted OSS / Institutional

Open source software, but hosted by an institution (a university, a nonprofit). You participate; you don't operate.

Protocol Client, Relay-Based

Connects to the Nostr relay network. Infrastructure costs only arise if you run your own relay.

Protocol Client, PDS-Based

Connects to the AT Protocol network. Infrastructure costs only if you run your own Personal Data Server.

Centralized Messaging

Open source software, centrally operated by the developer. Community = a group chat. No infrastructure costs.

Expected costs

How costs are derived

Rather than guessing costs platform by platform, costs are derived from each platform's type. The logic is simple: the main cost drivers are infrastructure ownership (do you host it?) and content type (does it generate heavy media?). Everything else — admin labor, third-party tools — applies broadly regardless of platform choice and depends more on your community's size and activity.

  • Self-hosting means you bear hosting, domain, email delivery, backups, and potentially managed hosting costs. Proprietary or institutionally-hosted platforms mean you bear none of these.
  • Media-heavy platforms (PeerTube, Pixelfed) add significant storage and delivery costs on top of the standard self-hosting baseline.
  • Protocol-native clients (Nostr, AT Protocol) have costs that only arise if you choose to run your own relay or Personal Data Server — most community runners won't.
  • Admin and moderation labor is the one cost that cuts across all platform types, because it follows community size and culture rather than technical architecture.

Some platforms have overrides where the type default isn't accurate — for example, Discourse requires SMTP for notifications (email delivery = Yes, not Sometimes), and Mailman is itself an email delivery system.

Structural models

The structural model describes how a platform's infrastructure is organized — who controls data, and how communication flows between participants.

ModelDescriptionExamples
CentralizedA single operator controls all data and infrastructure. The platform is one server (or cluster) owned and operated by one entity.Facebook, Reddit, Discord, Discourse (each instance)
FederationMultiple independently-operated servers interoperate via a shared open protocol. Each server is autonomous; users on different servers can still interact.Mastodon (ActivityPub), Matrix (homeservers), Mailman (email/SMTP)
RelayMessages are broadcast through relay nodes. Clients choose which relays to connect to and read from. There is no canonical server — the network is the relays.Damus, Amethyst, Primal (all Nostr)
Federation / RelayUses elements of both models. AT Protocol uses PDS-to-PDS federation for data storage, plus a relay layer (the firehose) for real-time distribution.Bluesky, Rsky (Blacksky)
Centralized / FederationA proprietary or institutionally-controlled platform built on top of a federation protocol. The platform itself is not self-hostable, but it interoperates with the broader protocol ecosystem.Roundabout (proprietary, built on AT Protocol)

Open source (OSI)

The Open Source Initiative (OSI) defines open source software as software whose license grants freedoms to use, study, modify, and distribute. The Open Source (OSI) column reflects whether the platform's software is released under an OSI-approved license.

A few cases worth noting:

  • Telegram — client apps are open source (GPLv3), but the server is proprietary and not published. Since the server is the operative component for a platform, Telegram is classified as not open source.
  • Signal — both client and server are AGPLv3, so it is open source. However, Signal controls the central infrastructure and the server is not practically self-hostable to interoperate with the main network, hence Self-Hostable = No.
  • Fandom — built on a proprietary fork of MediaWiki. Although MediaWiki itself is open source (GPLv2+), Fandom's modifications are not published under an OSI-compatible license.
  • Wikipedia — the MediaWiki software is open source (GPLv2+), but Wikipedia itself is hosted exclusively by the Wikimedia Foundation. The software label is open source; the platform is not self-hostable as Wikipedia.

Cost values

Cost columns use a five-point scale. All values reflect what a community organizer or operator typically pays — not the platform company.

ValueMeaning
YesThis cost reliably applies to community operators on this platform.
NoThis cost does not apply.
OftenApplies frequently, but not universally — varies by community size or activity level.
SometimesApplies in some configurations or at some scale, but not by default.
RareTechnically possible but uncommon in practice.

For corporate / proprietary platforms, costs reflect what a group admin or community manager pays — not the company operating the platform. For self-hosted platforms, costs reflect what an instance operator pays. For protocol client rows (Nostr, AT Protocol), costs reflect running your own relay or PDS; most community runners on these platforms will not incur infrastructure costs.
